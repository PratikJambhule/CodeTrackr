  {TypeScript, JavaScript, Node.js, Express.js, MongoDB, Mongoose, VS Code
   Extension API, REST APIs, OAuth 2.0, JSON Web Token (JWT)}
  {<DATES>}
  {%
  \begin{itemize}
    \item Built a \textbf{TypeScript} \textbf{VS Code extension} that passively
          measures coding activity through 5 event-driven trackers (editor
          edits and churn, terminal commands, Git commits, window focus, and
          debugger sessions), accumulating metrics in memory behind an
          idle/pause state machine and posting a consolidated, normalised
          record to a \textbf{REST} API about every 2 minutes of active coding
          --- transmitting only file basenames and sanitised command text so
          source code never leaves the machine.
    \item Designed the extension-to-backend ingestion path on \textbf{Node.js}
          / \textbf{Express.js}: per-user API-key authentication, additive
          payload normalisers that stay backward-compatible with older
          extension releases, and an atomic \texttt{\$inc} upsert that merges
          each flush into a 10-minute (user, project, language) \textbf{MongoDB}
          document --- cutting activity-record and write volume by roughly 10x
          with byte-identical totals, plus a 400-day time-to-live (TTL) index
          to bound growth.
    \item Developed a metrics service built on \textbf{MongoDB} \textbf{aggregation
          pipelines} and a unit-tested pure-function module that derives 5
          explainable productivity insights from the raw time-series events ---
          deep-work ratio, day-to-day consistency (coefficient of variation),
          true peak-productivity hour, estimate-vs-actual accuracy, and
          flow-block statistics --- using deterministic statistics rather than
          a black-box model.
    \item Secured the companion React dashboard with \textbf{Google OAuth 2.0}
          and \textbf{JWT} cookies and added per-route ownership checks on the
          analytics endpoints; covered the trackers, normalisers, and metrics
          functions with automated \texttt{node:assert} test suites, including
          a static scan that fails the build if a protected route loses its
          auth middleware.

%  * "Posts about every 2 minutes of active coding": the internal timer TICKS
%    every 30 s (flushIntervalSeconds), but a network send only happens once at
%    least 2 minutes of *active* coding time has buffered (minFlushMinutes,
%    default 2 since v2.3.0 -- it was 0.5 before), AND that interval carried a
%    real editor/terminal/Git/focus signal; a signal-less interval is withheld
%    and its time rolled into the next send. So on a wall clock the posts are
%    ~2 min apart during steady work and further apart when you pause. Say
%    "about every 2 minutes of active coding", never "every 30 seconds".
%
%  * The 10-minute bucketing bullet is your strongest system-design story:
%      - BEFORE: one Activity document per 30-90 s flush -> ~60-120 docs per user
%        per active hour, unbounded, each repeating metadata + four mostly-zero
%        analytics sub-objects.
%      - AFTER: an atomic findOneAndUpdate with \$inc into a document keyed by
%        (userId, projectName, language, bucketStart), bucketStart = the
%        timestamp floored to a 10-minute grid -> ~6-12 docs per user per hour.
%      - WHY TOTALS ARE UNCHANGED: \$inc.duration accumulates the REAL measured
%        seconds from each flush (45 + 60 = 105, never "1200"); only time-of-day
%        resolution drops to a 10-minute grid, finer than any chart renders.
%      - SAFETY: a partial-unique index on the bucket key; a duplicate-key
%        (11000) on first insert is caught and retried once as an update.
%      - ESCAPE HATCH: ACTIVITY_BUCKET_MS=0 restores one-doc-per-flush.
%      - The "~10x" is a document-count / write-count reduction by construction,
%        NOT a measured latency or throughput number. Say that plainly.

%  * "additive / backward-compatible normalisers": the backend
%    normalize{Editor,Focus,Git,Terminal}Analytics functions coerce every field

%    cleanly. Good "how do you handle client/server version skew" answer.
